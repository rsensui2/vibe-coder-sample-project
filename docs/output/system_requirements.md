# システム要件定義書

## システム概要
DORONUMAは、SNS上の過度なポジティブ文化に対するカウンターとして、「旅先や日常の失敗・トラブル・修羅場」を共有し、笑いと共感、そして実用的な防犯情報へと昇華させるWebアプリケーションです。ユーザーは自らの不運な出来事を「絶望メーター」と共に投稿し、コミュニティからの「災難だね」という共感や「供養（投げ銭）」を通じて、精神的なダメージを「称号」や資産へと変換します。同時に、投稿に紐づく位置情報を「失敗マップ（デンジャー・ゾーン）」として可視化することで、他のユーザーへのリアルな注意喚起を提供します。本システムは、モダンな技術スタックを採用し、モバイルファーストかつスケーラブルな構成で、失敗を最高の資産に変える新しい価値体験の提供を目指します。

1. システムの目的
   - 旅先や日常の失敗談を共有し、笑いと共感で精神的ダメージを浄化する。
   - リアルなトラブル情報を集約し、他ユーザーへの注意喚起・防犯情報として機能させる。
   - 失敗を「称号」や「ポイント」という資産に変えることで、ネガティブな体験に新しい価値を与える。

2. 主な機能
   - **コア機能**: ユーザー管理（称号システム）、ドロヌマ・ポスト（絶望メーター付投稿）、リアクション機能（「災難だね」）、タイムライン。
   - **差別化機能**: 失敗マップ（デンジャー・ゾーン）、不運の証明（公認失敗バッジ付与）。
   - **付加価値機能**: 供養（投げ銭・ギフト交換）、ドロヌマ・アワード（優秀失敗投稿の表彰）。

3. 提供する価値
   - **ユーザーにとっての直接的価値**: 失敗の共有によるストレス解消（カタルシス）、コミュニティからの共感、トラブル回避情報の取得。
   - **ビジネスにとっての価値**: 独自のコンテンツプラットフォーム構築、投げ銭手数料や旅行保険アフィリエイトによる収益化。
   - **社会的価値**: リアルタイムな危険情報の可視化による、旅行者・市民の安全向上。

4. 実現方法の概要
   - **主要なテクノロジー要素**: Next.js、TypeScript、Supabase、Clerk、Mapbox。
   - **重要なインテグレーションポイント**: Google/X 認証、Stripe（供養機能の決済）、Amazonギフト券等のAPI（ポイント交換）。
   - **スケーラビリティへの考慮**: Vercelによるエッジ配信、SupabaseによるスケーラブルなDB管理、CDNによる画像配信の最適化。

## 情報の前提と仮定
- **情報源**: `/docs/input/business_requrements.md`
- **仮定**:
  - 初期ターゲットユーザーはSNSに疲れを感じている20〜40代の日本人。
  - MVPフェーズでは国内旅行者および日常生活のトラブルに焦点を当て、多言語対応はフェーズ4以降とする。
  - 「不運の証明」の審査は、初期段階では人力および簡易的なAI判定で行う。

## 機能要件
- **FR-1: ユーザー管理**
  - Clerkを利用したメール/Google/X認証。
  - 投稿数・評価数に応じた称号システム（Lv.1〜Lv.5）。
- **FR-2: ドロヌマ・ポスト**
  - タイトル、本文（マークダウン）、カテゴリタグ（金銭、紛失、体調等）、絶望メーター（1-100%）。
  - 画像添付（最大5枚）、位置情報の紐付け、発生日の記録。
- **FR-3: 失敗マップ（デンジャー・ゾーン）**
  - Mapboxを使用した投稿位置のヒートマップ・ピン表示。
  - カテゴリや期間によるフィルタリング。
- **FR-4: リアクション・供養**
  - 「災難だね」「笑った」「供養」の3種リアクション。
  - 「供養」に伴う投げ銭機能と、ギフト券等への交換。
- **FR-5: ドロヌマ・アワード**
  - 週間・月間の優秀投稿自動算出および受賞バッジ付与。

## 非機能要件
- **NFR-1: パフォーマンス**
  - 初期ユーザー1,000人〜最大同時接続10,000人を想定。
  - LTE環境下で主要画面の読み込み時間を3秒以内とする。
- **NFR-2: セキュリティ**
  - JWTによる認証管理。HTTPS通信の強制。
  - 「不運の証明」に使用された個人情報書類は確認後即時削除する運用。
- **NFR-3: 可用性**
  - 稼働率99.5%以上を目標とし、日次バックアップを実施。
- **NFR-4: 法的遵守**
  - 投げ銭機能における資金決済法等の関連法規への準拠。
  - 利用規約およびプライバシーポリシーの整備（特に位置情報と個人書類の扱い）。

## 技術スタック
推奨されるモダンなスタックとして、開発効率とスケーラビリティを両立した以下を選定します。

- **フロントエンド:** Next.js (React) - SEO、パフォーマンス、開発体験のバランスが最適。
- **言語:** TypeScript - 堅牢な型定義により大規模化に伴うバグを抑制。
- **バックエンド:** Next.js App Router - フロントエンドとの親和性が高く、Server Actionsによる高速開発が可能。
- **データベース:** Supabase (PostgreSQL) - リアルタイム機能、認証、ストレージが統合されており、MVP開発の速度を最大化。
- **認証:** Clerk - 高度な認証・セッション管理を短期間で安全に実装可能。
- **ホスティング:** Vercel - Next.jsとの親和性が最高で、CI/CDの構築が容易。
- **地図表示:** Mapbox GL JS - 高度なカスタマイズが可能な地図描画エンジン。

## 開発ロードマップ
- **Phase 1: MVP（1〜3ヶ月）**
  - 根拠: 最小限の機能でユーザーの反応を検証（失敗投稿と共感のループ）。
  - 内容: 認証、基本投稿、タイムライン、リアクション。
- **Phase 2: コア機能強化（4〜5ヶ月）**
  - 根拠: 差別化要因であるマップ機能と、エンゲージメントを高める称号の実装。
  - 内容: 失敗マップ、称号システム、アワード。
- **Phase 3: 収益化（6〜7ヶ月）**
  - 根拠: ユーザー基盤が安定した段階でのマネタイズ開始。
  - 内容: 供養（投げ銭）機能、プレミアム会員、広告連携。

## リスク分析
- **リスク1（ビジネス）: 誹謗中傷・不適切投稿の蔓延**
  - 対策: 投稿ガイドラインの明示、通報機能の実装、AIによる自動モデレーション。
- **リスク2（技術）: 偽造された「不運の証明」による不正な称号獲得**
  - 対策: 審査プロセスの厳格化（段階的な自動化）、ユーザー信頼度スコアの導入。
- **リスク3（法的）: 位置情報の特定によるプライバシー侵害**
  - 対策: 位置情報の曖昧化（アバウトな円表示）オプションの提供。

## UI/UXの方向性
- **デザインコンセプト**: 「底なしの泥」をテーマにしつつ、洗練されたモダンさ。
- **トーン＆マナー**: ダークモード基調。ブラウンとイエローをアクセントにした「泥臭いが愛着の持てる」トーン。
- **ターゲットデバイス**: モバイルファースト。旅先での即時投稿を容易にするPWA対応。
- **参考サイト/アプリ**: Reddit (コミュニティ感)、X (タイムライン)、Google Maps (地図体験)。

## 追加情報リクエスト
- **高**: 供養ポイントの換金レートと、決済代行会社（Stripe等）との手数料調整の具体案。
- **中**: 「不運の証明」書類の具体的な審査基準（どの程度の書類まで認めるか）。
- **低**: プレミアム会員の価格設定に関する市場調査データ。
